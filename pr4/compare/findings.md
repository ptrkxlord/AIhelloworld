# Порівняння трьох конфігурацій

Скрипт `compare/run_compare.py` проганяє 9 звернень (7 одиночних + 2 діалоги по 4 репліки)
через три конфігурації запиту до моделі й зберігає сирі відповіді в `compare/results.json`.

Конфігурації:
1. **Нечіткий запит** — інструкція в один рядок, без формату відповіді, без правил магазину, без історії.
2. **Структурований prompt** — повна системна інструкція з обмеженнями, форматом і прикладами межових
   випадків, відповідь за JSON Schema, але без правил магазину і без історії розмови.
3. **Context engineering** — та сама інструкція плюс правила з `context.md`, історія розмови в межах
   бюджету токенів і перевірка відповіді за схемою (те саме, що робить `/api/chat`).

## Статус прогону

Реальний прогін проти Gemini на момент написання **не виконано**: наданий `LLM_API_KEY`
відхиляється безпосередньо Google —

```
403 PERMISSION_DENIED: Your project has been denied access. Please contact support.
```

Це підтверджено як через застосунок, так і прямим `curl`-запитом до
`https://generativelanguage.googleapis.com/v1beta/openai/chat/completions`, тобто причина не в
коді, а в самому ключі/проєкті Google AI Studio. Сам ключ також не має вигляду типового ключа
AI Studio (`AIzaSy...`), тож імовірно скопійовано не той рядок або доступ до проєкту призупинено.

Натомість конвеєр обробки перевірено ізольовано — підмінено виклик моделі на заглушку й
прогнано через `/api/chat`:
- валідний JSON за схемою приймається одразу;
- відповідь, обгорнута в \`\`\`json, коректно розпізнається (`_strip_fences`);
- невалідний JSON викликає один повторний запит з поясненням помилки, а якщо і він не
  проходить — клієнту йде безпечна заглушка з `escalate_to_human=true`, а не сирий текст;
  факт зафіксовано в журналі (`print("[validation-failure] ...")`);
  саме поле `schema_retry_used=true` в цьому прогоні підтвердило спрацювання повтору;
- номер замовлення в картці звернення "липкий": якщо нова відповідь не назвала номер,
  раніше зафіксований номер (`SHOP-048213`) залишається в `ticket.order_number`;
  збереження через `escalate_to_human=false or not grounded_in_rules` теж підтверджено;
- скорочення історії за бюджетом токенів лишає першу репліку розмови та стільки останніх,
  скільки влазить у бюджет — перевірено на штучній історії з 40+ реплік.

Щоб отримати реальні цифри порівняння, потрібно:
1. Отримати робочий ключ у https://aistudio.google.com (Get API key → Create API key) і
   вписати його в `LLM_API_KEY` у `pr4/.env`.
2. `pip install -r requirements.txt`
3. `python check_env.py` — переконатися, що провайдер приймає `response_format=json_schema`.
4. `python compare/run_compare.py` — заповнить `compare/results.json`.
5. Перенести фактичні значення (схема валідна/ні, тема, токени, час, чи згадано номер
   замовлення) у таблицю нижче й уточнити висновки за реальними даними.

## Очікувана відмінність між рівнями (гіпотеза до підтвердження реальним прогоном)

- **Нечіткий запит**: без схеми немає гарантії структури; без `context.md` немає на що спертись —
  очікується найбільша схильність вигадувати умови на q3 (розстрочка) і відповідати замість
  уточнення на q4 ("хочу повернути товар").
- **Структурований prompt**: схема й приклади мають прибрати синтаксичні помилки та стабілізувати
  `needs_clarification` на q4/q7, але без `context.md` для q3/q5 очікується `grounded_in_rules=false`
  замість вигаданої відповіді — модель чесно каже "не знаю", а не бреше.
- **Context engineering**: єдина конфігурація з історією розмови, тому лише вона має пройти
  останню репліку діалогів d1/d2 ("нагадайте номер замовлення") — номер там береться не з надії,
  що модель його "пам'ятає", а з серверної картки звернення, куди він потрапив ще на першій репліці.

Цю гіпотезу підтверджує або спростовує реальний прогін — після нього розділ вище треба замінити
на фактичні спостереження.

## Класифікація помилок (розділ 1 методички)

| Тип помилки | Де очікується/трапляється | Що в рішенні це ловить | Що не ловить |
|---|---|---|---|
| Синтаксична (не JSON, зайві/відсутні поля) | Нечіткий запит — модель не обмежена схемою, повертає вільний текст. Зрідка — структурований/context-режим, коли модель обгортає відповідь у \`\`\`json (підтверджено в ізольованому тесті). | `response_format=json_schema` знімає більшість випадків; `_strip_fences` прибирає огорожу з зворотних лапок; `AssistantReply.model_validate_json` — фінальна перевірка; при провалі — один повторний запит з текстом помилки (перевірено). | Якщо модель двічі поспіль повертає невалідний JSON — використовується безпечна відповідь-заглушка (`escalate_to_human=true`), а не справжня відповідь клієнту. |
| Семантична (поле заповнено не тим) | `topic` поза фіксованим переліком, `order_number` не в форматі SHOP-XXXXXX. | `Literal` у pydantic-схемі не дає моделі повернути тему поза переліком (провалить валідацію → повтор). Формат номера звіряється регулярним виразом і логується при розбіжності. | Регулярка лише логує розбіжність, не відхиляє відповідь — номер довільного формату, який усе ж є валідним рядком, дійде до картки звернення. |
| Фактична (вигаданий факт) | Очікувано на нечіткому запиті для q3 (розстрочка) — модель без правил схильна вигадувати умови. | Правила з `context.md` передаються окремим системним повідомленням; інструкція прямо забороняє вигадувати; приклад №2 у промпті показує очікувану поведінку. | Немає незалежної перевірки поля `grounded_in_rules`: код примусово ставить `escalate_to_human=true`, коли `grounded_in_rules=false` (перевірено), але не може довести, що `true` виставлено чесно — для цього потрібен окремий LLM-суддя або вибіркова ручна перевірка. |
| Контекстна (забула номер, змішала замовлення) | Нечіткий і структурований режими на останній репліці діалогів d1/d2 — історія взагалі не передається. | Context engineering зберігає історію на сервері й картку звернення (`order_number` — липке поле, підтверджено тестом, що не затирається порожнім значенням із нової репліки). | Якщо бюджет токенів вичерпано настільки, що навіть перша репліка не влазить, факт усе одно загубиться — рішення це не обробляє окремо. |
| Поведінкова (виконала вказівку клієнта змінити роль, не тією мовою, перевищила довжину) | Не спостерігалось — цільово не провокувалось у наявних сценаріях. | Інструкція явно каже ігнорувати вказівки клієнта змінити роль/формат/правила; обмеження довжини "2-4 речення" задане текстом інструкції. | Немає програмної перевірки мови відповіді чи кількості речень — обмеження лише в тексті інструкції, модель може його порушити непоміченою. |

## Висновки

Конвеєр (схема, повтор при невалідному JSON, безпечна заглушка, липкий номер замовлення в
картці, скорочення історії за бюджетом) перевірено ізольовано й працює коректно. Порівняння
трьох конфігурацій на реальних відповідях моделі не завершено через відхилений API-ключ —
таблиці вище підготовлені під фактичний прогін, і після отримання робочого ключа їх треба
заповнити результатами `python compare/run_compare.py`, а розділ "Очікувана відмінність" — замінити
на підтверджені або спростовані спостереження.
